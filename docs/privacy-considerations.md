# 個人情報保護に関する技術リファレンス

> 最終更新: 2026-05-05 (Phase 1-6 個人情報保護対応)
> 対象読者: 開発者・運用担当者
> 参照ドキュメント: [運用計画](plans/2026-04-28-operation-plan.md), [技術ガイド](technical-guide.md)

本ドキュメントは「シフトすけっと」の技術側面における個人情報保護の方針をまとめたリファレンスです。利用規約・プライバシーポリシー本文は別途整備されます（Phase 1-3）。

## 1. 取得する個人情報

| 項目 | 取得経路 | 利用目的 |
|------|---------|---------|
| メールアドレス | サインアップ時の Magic Link 認証 | 認証・通知 |
| ユーザー表示名 (任意) | プロフィール設定 | 画面表示 |
| スタッフ氏名 | 管理者がアプリに登録 | シフト表表示 |
| 勤務希望 | スタッフが入力 | シフト最適化 |
| シフト割当履歴 | 最適化結果として生成 | 公平性計算・履歴参照 |

第三者から個人情報を取得することはありません。

## 2. 利用目的

- シフト最適化のためのみ。マーケティング目的での二次利用なし。
- スタッフ間の希望シフトの可視化（管理者画面のみ）

## 3. 保管期間とライフサイクル

| イベント | 動作 |
|---------|------|
| 退会操作 (`/account/delete`) | 即座に User および所有 Organization 配下の全業務データを物理削除（Phase 1-8 で実装） |
| 12 ヶ月ログインなし | 休眠通知メール送信 (Phase 3 で実装予定) |
| 24 ヶ月ログインなし | 組織データ含めて完全削除 (Phase 3) |
| サービス終了 | 30 日前までに登録メール宛に通知し、CSV エクスポートを提供 |
| バックアップ保持 | 直近 7 日（Railway 日次バックアップ、Phase 1-5） |

## 4. 第三者提供・委託先

| 委託先 | 用途 | 配置 |
|--------|------|------|
| Vercel | フロントエンド配信 | アメリカ |
| Railway | バックエンド・DB ホスティング | アメリカ |
| Resend (Phase 1-2) | Magic Link 配信 | アメリカ |

国外移転に該当するため、利用規約への明記が必要（Phase 1-3）。

## 5. 暗号化方針

### 5.1 保管時暗号化 (At-Rest)

- **DB**: Railway Postgres の at-rest 暗号化（AES-256）標準で十分と判断。アプリケーション層暗号化は当面導入しない。
- **理由**:
  - スタッフ氏名・勤務希望は機密度が「中」程度（金融・医療情報ではない）
  - アプリ層暗号化は検索・最適化処理を阻害し、複雑度に対するメリットが薄い
  - 将来的に重要情報を扱う場合（給与等）に再評価する

### 5.2 転送時暗号化 (In-Transit)

- すべての通信は HTTPS / TLS（Vercel ↔ Railway 間も含む）
- HTTP はリダイレクトされる（Vercel デフォルト）

### 5.3 セッション暗号化

- Auth.js v5 の JWE (JSON Web Encryption) Cookie で暗号化済み
- Cookie 属性: `Secure`, `HttpOnly`, `SameSite=Lax`
- TTL: 30 日

## 6. ログマスキング (Phase 1-6)

`backend/backend/logging_config.py` の `SensitiveDataFilter` がアプリログ出力時に以下を伏せます:

| 対象 | マスキングパターン | 例 |
|------|-------------------|---|
| メールアドレス | `u***@d***.***` 形式 | `alice@example.com` → `a***@e***.***` |
| JWE トークン | 全体を `[JWE_TOKEN]` に置換 | `eyJhbGc...` → `[JWE_TOKEN]` |
| Magic Link / verification token | 32 文字以上の英数字列を `[TOKEN]` に置換 | 長い hex → `[TOKEN]` |
| URL クエリの `email=` / `token=` / `identifier=` / `callbackUrl=` | 値を `[MASKED]` に置換 | `?email=user@x.com` → `?email=[MASKED]` |

### 6.1 マスキングが効く範囲

- FastAPI / uvicorn のアクセスログ・エラーログ
- アプリケーションコード内の `logging` 呼び出し
- Pydantic バリデーションエラーで `exc_text` に乗る値

### 6.2 マスキングが効かない範囲（既知の制約）

- Sentry / Resend の SDK が独自に出力する内部ログ（Phase 1-4 / 1-2 統合時に各 SDK の設定で別途対応）
- DB 直接アクセス時のクエリログ（SQLAlchemy の `echo=True` を本番では使わない方針）
- 外部サービス（Railway, Vercel）のアクセスログ

## 7. 退会・データ削除 (Phase 1-8)

実装済み:
- `DELETE /api/me`: 自分のアカウントを削除（owner 組織と関連データを CASCADE で完全削除）
- `DELETE /api/organizations/{id}`: 自分が owner の組織を削除（関連業務データを CASCADE で完全削除）
- `/account/delete` UI: 確認フレーズ入力後にボタン有効化、誤操作抑止

メール窓口での削除請求受付は Phase 1-3 利用規約整備時に明文化予定。

## 8. 開示・訂正請求への対応

実装上の前提:
- 自分の情報は `/account` 配下のページから閲覧・編集可能（既存実装）
- 開示請求はメール窓口経由（Phase 1-3 で経路明示）

## 9. 適合する法令

- 個人情報の保護に関する法律（個人情報保護法）
- 特定電子メールの送信の適正化等に関する法律（メール送信時のオプトアウト導線）

## 10. 監査・モニタリング (Phase 1-4 で導入予定)

- Sentry でエラー収集、PII マスキング設定済（マスキングフィルタを Sentry SDK にも適用予定）
- アクセスログは Railway / Vercel の標準機能を活用（30 日保持）

## 11. インシデント対応

データ漏洩時:
1. 検知（Sentry / 外部通報）
2. 影響範囲特定（DB / ログ / バックアップ）
3. 個人情報保護委員会への通知（72 時間以内が目安）
4. 影響を受けたユーザーへの通知
5. 再発防止策の実施

詳細手順は Phase 1-5 バックアップ運用ドキュメント整備時に文書化。
