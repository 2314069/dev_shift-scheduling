# 運用計画 — 無料SaaSとして公開する

> 作成日: 2026-04-28 / ステータス: ドラフト / 担当: 1asato23@gmail.com

## 1. 目的・方針

本プロダクト（シフトスケジューリングWebアプリ）を **無料SaaS として一般公開** する。
招待制等のゲートは設けず、サインアップは誰でも可能とする。

### 立ち上げステップ
1. **公開準備（4/28〜6/7）** — 認証・マルチテナント・LP・規約・監視・バックアップを整備
2. **一般公開（6/7）** — 誰でもサインアップ可能な状態でローンチ
3. **公開後改善（6月中旬〜）** — 早期ユーザーのフィードバックを反映

### スコープの方針
- **やる**: 認証、マルチテナント、利用規約、最小限のLP、監視、バックアップ
- **やらない（フェーズ後送り）**: 課金、シフト交換申請、認証以外のフェーズ2機能

### Phase 0: 基盤整備（4/28〜5/12、約2週、~47h）

SaaSとして致命的に欠けている基礎を埋める。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 0-1 | 認証実装（Auth.js + Magic Link） | 18h | サインイン・サインアップフロー、セッション管理 |
| 0-2 | マルチテナント化（全テーブルに `organization_id`、API スコープ徹底） | 20h | DB マイグレーション、API 修正、E2E テスト追加、**solver テナント混在テスト** |
| 0-3 | 本番デプロイ動作確認（Vercel + Railway） | 6h | 本番環境で全機能の動作確認、環境変数整理、**自分で 2 組織作って混在オペで多テナント検証**（テナント越境バグの早期検出） |
| 0-4 | ドメイン取得・本番反映（着手前に J-PlatPat で商標確認） | 3h | `shift-suketto.jp` 取得、Vercel/Railway カスタムドメイン反映、SSL 確認、`.com` 防衛取得（任意）。**Phase 1-2 SMTP 設定（SPF/DKIM）が依存** |

> **Phase 0 完了ゲート**: マージ前に Reviewer エージェントによるセキュリティレビューを必ず実施し、テナント分離・認可漏れ・solver入力のテナント混在をチェックする。

> **0-2 工数内訳（参考）**: DB+リポジトリ 4h / スキーマ 1h / API 10ファイル 5h / solver+service 統合 2h / テスト書き直し+テナント分離テスト 4h / フロント `api.ts` 1h / マイグレーション準備 1h / セキュリティ確認 2h = 20h。

### Phase 3: 公開後改善（6月中旬〜）

早期ユーザーからのフィードバックを反映する。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 3-1 | フィードバック反映 | 可変 | 優先度の高いバグ修正・UX改善 |

## 4. 運用体制

### 障害対応
- **検知**: Sentry エラー通知をメール受信。アップタイム監視は β期は手動巡回 + ユーザー連絡で運用（Phase 3 以降で UptimeRobot 等の追加判断）
- **対応時間目標（β期間）**: 平日24h以内、休日48h以内（ベストエフォート）
- **連絡経路**: 利用規約に記載のメールアドレス

### バックアップ
- **頻度**: 日次（Railway DBダンプ）
- **保持期間**: 直近7日分
- **復旧手順**: ドキュメント化（Phase 1で作成）

### データ保持・アカウント方針
- **アクティブデータ保持期間**: 最終ログインから 24 ヶ月（その後削除）
- **休眠アカウント扱い**: 最終ログインから 12 ヶ月で休眠通知メール、24 ヶ月で組織データ含めて完全削除
- **退会時のデータ削除**: 退会操作後 7 日以内にバックアップを含めて完全削除
- **サービス終了時の通知**: 終了 30 日前までに登録メールアドレス全件へ事前通知、データエクスポート手段（CSV）を提供

### サポート
- **公開直後（6/7〜6月）**: 早期ユーザーには直接コンタクト（メール / Slack 等）+ お問い合わせ窓口で受付
- **それ以降**: メール窓口メイン（フォームで受付）

### モニタリング指標（最低限）
- サインアップ数 / アクティブ組織数（月次）
- 月次最適化実行数
- エラー発生率（Sentry）
- Magic Link 配信成功率（Resend ダッシュボードで監視、bounce/spam 率含む）

## 5. 法的事項

| 項目 | 対応 |
|------|------|
| 利用規約 | KIYAC（弁護士監修・無料プラン）で叩き台生成し、免責事項・禁止事項・データ保持方針を自前追記 |
| プライバシーポリシー | 個人情報（スタッフ氏名・メール）の取り扱い、Cookie 利用の明示 |
| 個人情報保護法 | 取得目的の明示、開示・訂正・削除請求への対応経路を `/account/delete` UI とメール窓口で提供（Phase 1-8） |
| 特商法表記 | **必須**。事業性ありと判断される可能性が高いため、`/legal` ページに事業者氏名・連絡先・住所を開示（住所はバーチャルオフィス活用も検討、Phase 2-4） |

> **規約の段階的高度化方針**: KIYAC ベースで当面運用し、月間アクティブ組織数が 100 を超えた時点で弁護士レビューを実施する判断軸とする。ユーザー数増加に伴い特商法・景表法（料金表示）・電気通信事業法の検討が新たに発生する可能性に注意。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|------|------|------|
| 工期遅延（6/7 に間に合わない） | 中 | 13h のリスクバッファで吸収。1-4/1-5/1-6 はリスク表（情報漏洩・データ消失）と整合性を取るため後ろ倒し不可、超過時は LP（2-1）の簡素化で吸収 |
| 認証・マルチテナント実装でバグ | 高（情報漏洩リスク） | テスト追加、Reviewer エージェントによる Phase 0 完了ゲートでのセキュリティレビュー必須 |
| 初期ユーザーが集まらない | 中 | 知り合いの店舗・X（旧Twitter）で告知。SNS 経由の流入を主な集客経路と想定 |
| 公開直後の重大バグ顕在化（friendly テストを省略したため） | 中 | Phase 0-3 の本番デプロイ動作確認 + セルフ多テナント検証を入念に実施、Sentry でランタイムエラー即検知 |
| データ消失 | 高 | Phase 1 でバックアップ自動化を必ず完了（後ろ倒し不可） |
| メール配信の信頼性（Magic Link が spam 入りするとログイン不可） | 中 | Resend を採用。Phase 0-4 でドメイン取得後、Phase 1-2 で SPF/DKIM/DMARC 設定。Resend ダッシュボードで配信成功率を監視。月3,000通超で有料切替判断 |
| 法的トラブル（個人情報・規約・特商法不備） | 高 | KIYAC ベース規約 + 特商法表記必須化（Phase 2-4）+ 削除請求受付経路（Phase 1-8）。データ最小化原則の徹底 |
