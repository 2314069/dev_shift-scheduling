# 運用計画 — 無料SaaSとして公開する

> 作成日: 2026-04-28 / ステータス: ドラフト / 担当: 1asato23@gmail.com

## 1. 目的・方針

本プロダクト（シフトスケジューリングWebアプリ）を **無料SaaS として一般公開** する。
ただし、いきなり公開せず段階的に立ち上げてリスクを抑える。

### 立ち上げステップ
1. **ソフトローンチ（5月末）** — 招待制βで限定ユーザーに使ってもらう
2. **一般公開（6月）** — 誰でもサインアップ可能に

### スコープの方針
- **やる**: 認証、マルチテナント、利用規約、最小限のLP、監視、バックアップ
- **やらない（フェーズ後送り）**: 課金、シフト交換申請、認証以外のフェーズ2機能

### Phase 0: 基盤整備（4/28〜5/10、約2週、~40h）

SaaSとして致命的に欠けている基礎を埋める。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 0-1 | 認証実装（Auth.js + Magic Link） | 18h | サインイン・サインアップフロー、セッション管理 |
| 0-2 | マルチテナント化（全テーブルに `organization_id`、API スコープ徹底） | 16h | DB マイグレーション、API 修正、E2E テスト追加 |
| 0-3 | 本番デプロイ動作確認（Vercel + Railway） | 6h | 本番環境で全機能の動作確認、環境変数整理 |

### Phase 1: SaaS化（5/11〜5/24、約2週、~30h）

招待ユーザーが安心して使える状態にする。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 1-1 | オンボーディング（サインアップ→組織作成→初期データ投入ガイド） | 10h | 新規サインアップから設定完了までのフロー |
| 1-2 | SMTP 設定（Magic Link 配信） | 4h | Resend or SendGrid 等の選定・本番組み込み |
| 1-3 | 利用規約・プライバシーポリシー作成 | 8h | `/terms` `/privacy` ページ、サインアップ時同意 |
| 1-4 | 監視（Sentry エラー収集） | 2h | フロント・バックエンド両方に組み込み |
| 1-5 | バックアップ自動化（Railway DB ダンプ日次） | 4h | cron / Railway 機能で日次バックアップ |
| 1-6 | 個人情報保護対応（DB暗号化方針確認・最低限のログマスキング） | 4h | スタッフ氏名等の取り扱い方針ドキュメント化 |

### Phase 2: ソフトローンチ準備（5/25〜5/31、約1週、~20h）

招待制βを開始する。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 2-1 | サービス名・ドメイン決定・取得 | 3h | カスタムドメイン本番反映 |
| 2-2 | シンプルなLP（README レベル） | 6h | `/` のランディング、特徴・スクリーンショット |
| 2-3 | 招待コード機能 or 招待リンク（ベータ期間中だけサインアップ制限） | 4h | 招待コードないとサインアップ不可 |
| 2-4 | ドキュメント整備（`docs/usage-guide.md` を実態に合わせる） | 3h | 最新版の使い方ガイド |
| 2-5 | ベータユーザー数名（3〜5店舗）に招待・実地利用 | 4h | フィードバック収集チャネル準備（フォーム or メール） |

### Phase 3: 一般公開（6月）

フィードバックを反映しつつ、招待制限を外す。

| # | タスク | 見積 | 成果物 |
|---|------|------|-------|
| 3-1 | β期間のフィードバック反映 | 可変 | 優先度の高いバグ修正・UX改善 |
| 3-2 | 招待制限の解除 | 1h | 設定変更のみ |
| 3-3 | LP 拡充（FAQ、料金（無料）、お問い合わせ） | 8h | 公開前提のLP |
| 3-4 | お問い合わせ窓口（メール or フォーム） | 2h | サポート受付経路の明示 |

## 4. 運用体制

### 障害対応
- **検知**: Sentry エラー通知をメール受信
- **対応時間目標（β期間）**: 平日24h以内、休日48h以内（ベストエフォート）
- **連絡経路**: 利用規約に記載のメールアドレス

### バックアップ
- **頻度**: 日次（Railway DBダンプ）
- **保持期間**: 直近7日分
- **復旧手順**: ドキュメント化（Phase 1で作成）

### サポート
- **β期間**: 招待時に直接メール / Slack 等で個別対応
- **一般公開後**: メール窓口のみ（フォームで受付）

### モニタリング指標（最低限）
- サインアップ数
- 月次最適化実行数
- エラー発生率（Sentry）

## 5. 法的事項

| 項目 | 対応 |
|------|------|
| 利用規約 | テンプレートをベースに自作。免責事項・禁止事項・データ保持方針を含める |
| プライバシーポリシー | 個人情報（スタッフ氏名・メール）の取り扱い、Cookie 利用の明示 |
| 個人情報保護法 | 取得目的の明示、削除請求への対応経路を用意 |
| 特商法表記 | 無料サービスでも事業者情報の開示が望ましい（任意） |

> **要検討**: 弁護士レビューはコストが嵩むので、初期は OSS の規約テンプレ（example: 法務テンプレ集）を流用し、本番ユーザー数が一定数を超えたら専門家に相談する判断も視野に。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|------|------|------|
| 工期遅延（5月末に間に合わない） | 中 | Phase 1 の 1-4・1-5・1-6 を Phase 3 に後ろ倒し可能 |
| 認証・マルチテナント実装でバグ | 高（情報漏洩リスク） | テスト追加、Reviewer エージェントによるセキュリティレビュー必須 |
| ベータユーザーが集まらない | 中 | 知り合いの店舗・X（旧Twitter）で募集 |
| データ消失 | 高 | Phase 1 でバックアップ自動化を必ず完了 |
| メール配信の信頼性 | 中 | 送信ドメイン認証（SPF/DKIM）、Resend 等の信頼性高い業者を選ぶ |
| 法的トラブル（個人情報・規約） | 高 | 規約に免責を入れる、データ最小化原則の徹底 |
